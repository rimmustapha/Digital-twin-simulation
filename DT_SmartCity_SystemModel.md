# System Model: AI-Empowered and Secure Digital Twin for Monitoring and Anomaly Detection in Smart Cities

## 0. Positioning relative to the baseline paper

Ren et al. (2025) propose an edge-cloud collaborative DTN where each task can be **split** between an MEC server and the MCC server, optimized with PPO over a continuous bandwidth-allocation action space, with a single scalar objective (latency) and no notion of task type, security, or migration. Your thesis targets a different, more realistic setting: **smart-city anomaly detection**, where security and cost matter as much as latency, tasks are heterogeneous (routine telemetry vs. alarms), and a task cannot be arbitrarily split — it must be *placed* on exactly one execution site, with the possibility of *moving* it if that site becomes infeasible. The model below is built to make those distinctions explicit and formal.

---

## 1. System Architecture

### 1.1 Layers

1. **Physical/IoT layer** — `K` heterogeneous sensing devices (traffic cameras, air-quality sensors, smart-grid meters, water-network sensors, structural sensors) deployed across `Z` city zones.
2. **Edge layer** — `M` edge servers (one per zone, or one per cluster of zones), each hosting a lightweight **Edge Digital Twin Agent (E-DTA)**: a partial twin of its zone plus a fast anomaly-detection model.
3. **Cloud layer** — **one** cloud data center hosting the **Global Digital Twin (G-DT)**: the full-fidelity twin of the city, heavier deep models, historical data lake, and the orchestration/training logic.
4. **Security & orchestration plane** — cross-cutting layer (not a physical tier) that issues trust scores, encryption policies, and the placement/migration decisions. This is the layer your RL agent controls.

### 1.2 Edge server characteristics (heterogeneous, not identical)

Recommended default for simulation — `M = 8` edge servers, one per zone type, with three tiers so the placement problem is non-trivial:

| Tier | # servers | CPU | RAM | Storage | Local link to devices | Backhaul to other edges | Backhaul to cloud | Security level `S_m` |
|---|---|---|---|---|---|---|---|---|
| Light edge (e.g., street cabinet) | 3 | 4-core, 2.0 GHz | 8 GB | 256 GB SSD | Wi-Fi 6 / 5G, ~500 m radius | 1 Gbps fiber ring | 1 Gbps | 1 (basic TLS) |
| Standard edge (substation/junction hub) | 3 | 8-core, 2.6 GHz (+ optional small GPU/NPU) | 16 GB | 512 GB SSD | 5G, ~1 km radius | 1 Gbps fiber ring | 2 Gbps | 2 (TLS + HSM key storage) |
| Heavy edge (district data closet) | 2 | 16-core, 3.0 GHz + GPU | 32 GB | 1 TB SSD | 5G, ~2 km radius | 10 Gbps fiber ring | 5 Gbps | 3 (TLS + HSM + local IDS) |

### 1.3 Cloud server characteristics

One logical cloud endpoint (can be a data-center cluster abstracted as one node):
- CPU: 64+ cores, 3.5 GHz aggregate, GPU cluster for retraining deep anomaly-detection models.
- RAM: 512 GB+, storage: petabyte-scale data lake.
- Security level `S_c = 3` (highest — dedicated SOC, full audit trail, hardware security modules).
- Backhaul: high bandwidth (≥10 Gbps) but higher **propagation** latency than edge-edge links (`T^{prop}`, e.g. 5–20 ms depending on geography), whereas edge-edge links are near-metro (≈1–3 ms).

This gives you a genuine trade-off: cloud has more compute and top security, but higher fixed latency and higher marginal monetary cost; edges are cheap and fast but capacity- and security-limited.

## 2. Task Model

Every task is generated by a terminal `k` and belongs to exactly one of two classes.

### 2.1 Periodic tasks (DT state-synchronization)

Generated every `T_sync` (e.g. 1–5 s) by routine sensors: telemetry updates that keep the twin's state current (temperature, flow, occupancy, meter readings). Characteristics: small-to-medium data size, loose deadline, low-to-medium security requirement, low priority, statistically predictable arrival.

### 2.2 Event-driven tasks (anomaly / alarm)

Triggered asynchronously by a threshold breach, a suspected intrusion, or a sudden state change (e.g., abnormal traffic pattern, gas-leak signature, unauthorized access to a substation controller). Characteristics: larger/heavier inference (may need a deeper model than the periodic one), **tight deadline**, high security requirement, high priority, unpredictable arrival (modeled as a Poisson process with rate `λ_event`).

### 2.3 Formal task tuple

For task `k` generated at time `t`:

$$J_k(t) = \{ type_k,\; I_k,\; C_k,\; T_k^{max},\; \sigma_k,\; \rho_k \}$$

- `type_k ∈ {PER, EVT}`
- `I_k` — input data size (bits)
- `C_k` — CPU cycles required (depends on `type_k`: `EVT` tasks use a heavier detection model ⇒ larger `C_k`)
- `T_k^{max}` — deadline (loose for `PER`, e.g. 200–500 ms; tight for `EVT`, e.g. 20–50 ms)
- `σ_k ∈ {1,2,3}` — minimum required security level (data sensitivity: e.g. a substation intrusion alert needs `σ_k = 3`; a routine air-quality reading needs `σ_k = 1`)
- `ρ_k` — priority weight, used for scheduling when multiple tasks compete for the same node (`EVT ≫ PER`)

## 3. Security Model

### 3.1 Node security level

Each edge server `m` and the cloud `c` has a static **security capability level** `S_m ∈ {1,2,3}` (Section 1.2/1.3), reflecting its hardware root of trust, encryption stack, and physical exposure (a street-cabinet edge is more physically exposed than a hardened district closet).

### 3.2 Dynamic trust score

Each node also carries a **dynamic trust score** `Tr_m(t) ∈ [0,1]`, updated periodically from a lightweight local intrusion-detection/reputation mechanism (e.g., anomaly rate in the node's own behavior, failed-auth attempts, patch status):

$$Tr_m(t) = (1-\eta)\,Tr_m(t-1) + \eta \cdot g_m(t)$$

where `g_m(t) ∈ [0,1]` is the instantaneous health signal from the local IDS and `η` is a smoothing factor. `Tr_m` lets the system penalize a *nominally* high-security node that is currently behaving suspiciously, even before its `S_m` rating is formally downgraded.

### 3.3 Feasibility constraint

A task can only be placed on a node whose security level meets its requirement:

$$S_{node} \geq \sigma_k$$

### 3.4 Security overhead (cost of protecting the task, not just gating it)

Higher `σ_k` implies stronger encryption/authentication, which costs time. Model it as an extra delay term proportional to data size and to a per-level encryption rate `e(σ_k)` (e.g., AES-128 for level 1, AES-256 for level 2, AES-256 + mutual-attestation handshake for level 3):

$$T_k^{sec} = \frac{I_k}{e(\sigma_k)}$$

### 3.5 Residual risk term

Even when the feasibility constraint holds, placing a sensitive task on a lower-trust node should be discouraged rather than merely allowed/forbidden. Define a **risk cost**:

$$Risk_k(node) = \sigma_k \cdot \big(1 - Tr_{node}(t)\big)$$

This term feeds directly into the optimization objective (Section 6), so the system prefers the most trustworthy *feasible* node, not just any feasible one.

## 4. Latency Model (no splitting — one full path per task)

Because a task is never split, each task follows exactly **one** of three paths: local edge, migrated edge, or cloud. Reuse the paper's Shannon-capacity link model, but compose it per-path instead of per-fraction.

**Link rate (generic, device→node or node→node):**
$$R_{a,b} = B_{a,b}\log_2\left(1+\frac{P_a\|h_{a,b}\|^2}{N_0}\right)$$

### 4.1 Path A — Local edge execution (`x_{k,m}=1`)
$$T^{up}_{k,m} = \frac{I_k}{R_{k,m}}, \qquad T^{comp}_{k,m} = \frac{C_k}{f_m^E}$$
$$T_k^{A} = T^{up}_{k,m} + T_k^{sec} + T^{comp}_{k,m}$$

### 4.2 Path B — Migrated edge execution (`z_{k,m\to m'}=1`)
Task first reaches its "home" edge `m`, then is forwarded over the edge-edge backhaul to a neighboring edge `m'` with spare capacity or higher security:
$$T^{mig}_{m,m'} = \frac{I_k}{R_{m,m'}}, \qquad T^{comp}_{k,m'} = \frac{C_k}{f_{m'}^E}$$
$$T_k^{B} = T^{up}_{k,m} + T^{mig}_{m,m'} + T_k^{sec} + T^{comp}_{k,m'}$$

### 4.3 Path C — Cloud offload (`y_{k,c}=1`)
$$T^{up}_{m,c} = \frac{I_k}{R_{m,c}}, \qquad T^{comp}_{k,c} = \frac{C_k}{f_c}$$
$$T_k^{C} = T^{up}_{k,m} + T^{up}_{m,c} + T^{prop} + T_k^{sec} + T^{comp}_{k,c}$$

### 4.4 Unified expression
With binary placement indicators `x_{k,m}, z_{k,m,m'}, y_{k,c} \in \{0,1\}` and exactly one equal to 1 per task:

$$T_k^{total} = x_{k,m}\,T_k^{A} + z_{k,m,m'}\,T_k^{B} + y_{k,c}\,T_k^{C}$$

with the hard deadline constraint `T_k^{total} \le T_k^{max}` (strict for `EVT`, relaxed penalty allowed for `PER`).

## 5. Monetary Cost Model

$$Cost_k = \underbrace{C_k \cdot p_m^{E}}_{\text{if edge}} \;\text{ or }\; \underbrace{C_k \cdot p_{m'}^{E} + \gamma_{mig}}_{\text{if migrated}} \;\text{ or }\; \underbrace{C_k \cdot p_c + I_k\cdot p_{tx}}_{\text{if cloud}}$$

- `p_m^E` — per-cycle cost at edge `m` (low, amortized hardware/energy).
- `p_c` — per-cycle cost at the cloud (pay-as-you-go, typically `p_c > p_m^E`).
- `γ_mig` — fixed migration overhead (orchestration + backhaul reservation).
- `p_tx` — data-egress cost to the cloud (edge-cloud transfer is usually billed; edge-edge and device-edge are not).

---

## 6. Joint Optimization Problem

**Decision variables:** `x_{k,m}`, `z_{k,m,m'}`, `y_{k,c}` ∈ {0,1} for every task `k`.

$$\min_{x,z,y} \;\Psi = \sum_{k=1}^{K} \Big[ w_1 T_k^{total} + w_2\, Cost_k + w_3\, Risk_k \Big]$$

subject to:

- **C1 (single placement):** `x_{k,m} + \sum_{m'} z_{k,m,m'} + y_{k,c} = 1, \; \forall k`  *(no splitting — exactly one full path chosen)*
- **C2 (deadline):** `T_k^{total} \le T_k^{max}, \; \forall k`
- **C3 (edge capacity, per time slot Δt):** `\sum_{k: x_{k,m}=1} C_k \le f_m^E \cdot \Delta t, \; \forall m` (same for tasks migrated *into* `m`)
- **C4 (security feasibility):** `S_{node(k)} \ge \sigma_k, \; \forall k`
- **C5 (bandwidth):** `0 \le B_{k,m} \le B^{max}`, and similarly for edge-edge and edge-cloud links
- **C6 (budget):** `\sum_k Cost_k \le Budget`
- **C7 (migration reachability):** `z_{k,m,m'}=1` only if `m'` is a defined neighbor of `m` in the edge topology

The weights `w_1, w_2, w_3 \ge 0`, `w_1+w_2+w_3=1`, let you trade off latency, cost, and security risk explicitly (e.g., set `w_3` high for critical-infrastructure zones) — this directly generalizes the baseline paper's `λ` switch, which only ever isolated one term at a time.

---

## 7. Placement & Migration Logic

Rather than a free joint search over all three paths for every task (expensive and not how real orchestrators behave), use the layered decision the thesis asks for:

1. **Attempt local edge (Path A).** If C2–C4 are satisfiable at the task's home edge `m`, place it there.
2. **Else, attempt migration (Path B).** Search `m`'s neighbor set for an edge `m'` that satisfies C2–C4 (more spare capacity, or higher `S_{m'}` if the local edge lacks the needed security level). If found, migrate.
3. **Else, offload to cloud (Path C).** The cloud always satisfies `S_c = 3` and effectively unlimited capacity, so it is the fallback of last resort — at the price of higher latency and cost.

This is exactly the gap you flagged in the baseline (which only ever *splits* a task locally + remotely, never *relocates* it): here, migration is a distinct, capacity/security-triggered decision, and cloud offload is a full relocation, not a partial one.

## 8. Learning Algorithm: from single-agent PPO to Multi-Agent PPO (MAPPO)

### 8.1 Why the original PPO setup doesn't fit directly

In the reference paper, PPO is well suited because the action space is **continuous** (bandwidth split `α_k`, `W_{ku}`, `W_{kd}`) and there is a single centralized decision-maker. In your model the action space is **discrete and combinatorial** (choose one of `M+1` execution sites, or a "migrate" sub-choice among neighbors), and decisions are naturally **distributed**: each edge server observes its own queue, its own trust score, and its immediate neighbors, not the whole city.

### 8.2 Recommendation: keep the PPO family, move to Multi-Agent PPO (MAPPO)

Rather than switching to a different algorithm family, adapt PPO to this setting for two reasons: (1) PPO's clipped surrogate objective remains one of the most stable choices when rewards are shaped from multiple, sometimes conflicting terms (latency, cost, risk) — off-policy methods like DQN tend to be less stable under such composite, sparse-event (`EVT` task) reward signals; (2) PPO extends naturally to **categorical (discrete) policies** via a softmax action head, so no fundamental change to the algorithm's mechanics is needed, only to the action representation.

The structural change is **single-agent → multi-agent**, using the standard **Centralized-Training, Decentralized-Execution (CTDE)** pattern:
- **Agents:** each of the `M` edge servers is an independent policy (weight sharing is fine given homogeneity within a tier).
- **Local observation** `o_m(t)`: own queue backlog, own trust score `Tr_m(t)`, own remaining capacity, and the *advertised* state of its direct neighbors (backlog + trust) — not the whole city, which keeps the observation space realistic for a real deployment.
- **Action** `a_m(t) \in \{\text{keep-local}, \text{migrate to } m'_1, ..., \text{migrate to } m'_n, \text{offload-cloud}\}` — a discrete choice per incoming task.
- **Centralized critic** (training-time only): sees the global state to compute a shared advantage estimate, stabilizing training across agents; discarded at inference, when each edge acts on local observations only — matching how a real smart-city edge deployment would actually operate (no global synchronous view at runtime).
- **Reward:** `r_m(t) = -\big(w_1 T_k^{total} + w_2\, Cost_k + w_3\, Risk_k\big)` for each task handled by `m`, plus a hard penalty if C2 (deadline) or C4 (security) is violated, and a small bonus for successfully resolving an `EVT` task within deadline (to bias learning toward protecting anomaly-detection latency specifically, which is the whole point of the thesis).

This keeps your contribution clearly framed as an *evolution* of the baseline's RL design — same family (PPO), same stability guarantees, but restructured for a discrete, distributed, security-aware placement/migration problem instead of a centralized continuous bandwidth split.
